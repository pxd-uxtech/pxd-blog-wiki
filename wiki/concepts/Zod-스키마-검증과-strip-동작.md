# Zod 스키마 검증과 strip 동작

**Zod**는 런타임에 데이터를 검증하고 같은 스키마에서 TypeScript 타입(`z.infer`)을 만들어 주는 라이브러리다. TypeScript 타입은 컴파일 후 사라지므로 API 응답, 쿼리스트링, 폼 입력, 환경변수처럼 코드 바깥에서 들어오는 값은 런타임 검사가 따로 필요하다. 이런 경계에서 한 번 파싱해 신뢰 가능한 타입으로 바꾸고 이후 코드는 그대로 쓰는 접근이 **Parse, don't validate**이며, `as User` 같은 타입 단언은 값을 검사하지 않는다.

핵심은 `z.object`의 기본 동작인 **strip**이다. 스키마에 없는 키는 에러나 경고 없이 결과에서 제거된다. `parse()`는 입력 객체를 수정하지 않고 알려진 키만 담은 새 객체를 반환하므로, 이후 로직이 이 반환값을 쓰면 제거된 값은 도달하지 않는다. 모드는 세 가지다. 기본 strip, 모르는 키를 유지하는 `z.looseObject`(Zod 3의 `.passthrough()`), 모르는 키에 에러를 내는 `z.strictObject`(Zod 3의 `.strict()`).

실전 사례: 프론트가 `interval=1`을 보냈는데 응답은 계속 10분 간격이었다. 스웨거에서는 정상 동작했고 Network 탭에도 값이 있었다. 원인은 프론트와 백엔드 사이 BFF/프록시의 `ChartQuery` 스키마에 `interval`이 없어 strip으로 제거된 것이었다. 스웨거는 프록시를 거치지 않고 백엔드를 직접 호출해서 정상이었다. 수정은 `z.coerce.number().int().positive().optional()` 한 줄이었다.

## 핵심 내용
- 검증 스키마는 **화이트리스트**다. 파라미터를 end-to-end로 추가할 때는 프론트 → 프록시 스키마 → 백엔드 모든 레이어가 해당 필드를 알아야 한다.
- 경계의 성격에 따라 모드를 고른다. 값을 **소비**하는 경계는 strict가 실수를 조기에 드러내고, 값을 **전달**하는 릴레이 경계(프록시·BFF)는 loose가 누락을 막는다. strip을 유지한다면 의식적인 선택이어야 한다.
- 쿼리스트링 값은 항상 문자열이므로 `z.coerce.number()`가 필요하다. 다만 빈 문자열은 0, 잘못된 문자열은 NaN이 되므로 `.int().positive()` 같은 제약을 붙인다.
- `.optional()`은 undefined를 먼저 걸러 내부 스키마를 호출하지 않는다. 프록시에서 `.default()`로 값을 만들면 백엔드 기본값을 쓰려는 의도와 달라진다.
- 요청에는 있는데 응답에 반영되지 않으면 프록시, 검증 스키마, 어댑터, 캐시 등 중간 레이어를 순서대로 확인한다. 스웨거(직통)와 프론트(경유)의 경로 차이가 단서가 된다.
- react-query의 `queryKey`에 파라미터가 빠지면 값이 바뀌어도 리페치되지 않는다. 별개의 버그이므로 원인이 둘이면 하나를 고치고도 증상이 남을 수 있다.
- Zod 4 변경점: `z.email()` 등 최상위 포맷 함수, 포맷 오류 code가 `invalid_format`으로 통합. strip 기본값은 Zod 3·4 동일.
