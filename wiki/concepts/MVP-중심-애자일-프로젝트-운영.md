# MVP 중심 애자일 프로젝트 운영

디지털 전환 프로젝트를 1년간 리드한 실무 경험에서, 새로운 디지털 기술(AI·클라우드·빅데이터)이 기존 시스템에 적용될 때는 시스템 통합(PI/SI) 관점이 아니라 사용자 관점에서 프로덕트를 바라보는 접근이 필요하다는 문제의식이 출발점이 된다. 여기서 제시되는 실행 원칙은 완성된 기능을 한 번에 설계하기보다, 기존 사용자 여정과 각 행동의 **멘탈 모델**을 먼저 이해하고, 기존 화면·용어·기능의 재사용 여부를 판단한 뒤, 최소한의 기능만 담은 **MVP(Minimum Viable Product)**를 먼저 릴리즈해 실제 데이터를 보고 개선 방향을 정하는 순서다. 디지털 전환이 특히 사용자 데이터를 새로 확보하기 좋은 국면이라는 점에서, 완벽을 기하기보다 빠르게 MVP를 내놓고 이후 데이터 기반으로 디벨롭하는 흐름이 유효하다고 강조한다.

프로젝트 실행 방식으로는 **디자인이 스프린트의 시작점이 되는 구조**가 소개된다. 퍼블리셔·프론트엔드·백엔드 개발자와 함께 2주 단위 스프린트를 사용자 인터뷰·관찰조사 기반의 **Functional Design** 설계 → 프로토타입 테스트(1:1 또는 그룹 인터뷰)로 서비스 시퀀스 확정 → 개발 아키텍처용 가이드와 GUI 디자이너용 **Perception Design** 드래프트 동시 전달 → 완성된 화면이 포함된 최종 가이드 배포 순으로 진행한다. 대부분의 프로젝트가 디자인에서 시작되는 만큼, 디자이너가 역량에 따라 스프린트를 직접 리드할 수 있다면 프로젝트가 더 원활해질 수 있다고 보며, 이런 배경이 최근 **프로덕트 디자이너·프로덕트 오너** 직군의 인기로 이어진다고 해석한다.

서로 다른 사고방식·업무 방식·소속을 가진 다수의 이해관계자와 협업하는 과정에는 **UX적 관점의 커뮤니케이션 설계**가 필요하다는 점도 강조된다. **지라(Jira)** 같은 도구로 태스크와 담당자·진행 상태를 투명하게 공유하면 협업 효율이 높아지고, 개발 가이드 문서는 디자이너가 일방적으로 전달하는 산출물이 아니라 개발자와 함께 맞춰가며 만드는 최종 결과물로 다뤄야 하며, 가이드 1.0을 완성 시점이 아니라 MVP 개발을 위한 중간 문서로 보고 이후 **VoC(Voice of Customer)** 대응을 운영팀과 지속적으로 논의해야 한다고 정리한다. 결국 UX의 가치는 사용자 경험 개선 자체뿐 아니라, 프로세스에 관여하는 이해관계자들에게 무엇이 어떻게 개선되는지를 효과적으로 전달하는 데에도 있다는 점, 그리고 빠른 프로토타이핑으로 아이디어를 직접 보고 만지게 하는 것의 힘을 재확인했다는 회고로 마무리된다.

## 핵심 내용
- 시스템(PI/SI) 관점이 아닌 **사용자 관점**에서 디지털 전환 프로젝트에 접근
- 실행 순서: 사용자 여정·멘탈모델 이해 → 기존 요소 재사용 여부 판단 → **MVP** 우선 릴리즈 → 데이터 기반 개선
- 디자인이 2주 단위 스프린트의 시작점이 되는 구조: Functional Design → 프로토타입 테스트 → 개발 가이드·Perception Design 전달 → 완성 가이드 배포
- 디자이너가 스프린트를 리드할 수 있는 역량이 **프로덕트 디자이너/프로덕트 오너** 직군의 부상과 맞닿아 있음
- **지라(Jira)** 등을 활용한 투명한 태스크 관리가 다자간 커뮤니케이션 효율을 높임
- 개발 가이드 문서는 일방적 전달물이 아니라 개발자와 함께 만드는 협업 산출물이며, 완성이 아닌 **VoC 대응을 위한 지속 갱신 문서**로 취급
- UX의 가치는 경험 개선 자체뿐 아니라 이해관계자에게 개선 내용을 잘 전달하는 데에도 있음
