# 앱 개발 사례 — 멀티 스크린 디바이스

pxd **LeanUXLab**(현 Lean UX Lab)이 2014년에 진행한 **멀티 스크린 디바이스** 실험 프로젝트의 개발 후기다. 계기는 랩 멤버가 PDF 전자책을 한 페이지씩 넘겨보는 데 답답함을 느끼며 종이책처럼 두 페이지를 동시에 볼 수 있는 전자책을 원한 데서 출발했다. 책이라는 형태가 오랫동안 살아남은 이유를 "작게 접어 휴대하고 펼쳐서는 넓은 정보 공간을 쓰는 효과적인 디자인 패턴"으로 해석하고, 스마트폰·태블릿·PC·TV 등 개인이 여러 스크린을 동시에 보유하게 된 흐름 속에서 여러 대의 디바이스를 네트워크로 연결해 하나의 콘텐츠를 공유하는 인터랙션을 직접 만들어보며 연구하는 것이 프로젝트의 목표였다.

개발은 제품의 완성형을 미리 상세히 설계하지 않고, 가장 기본이 되는 기능부터 단계적으로 구현한 뒤 테스트·수정을 반복해 발전시키는 **MVP** 방식으로 진행됐다. 첫 단계는 네트워크로 연결된 두 대의 디바이스에서 하나의 PDF를 함께 보는 **듀얼스크린 PDF 뷰어**로, PDF 렌더링 → 디바이스간 통신 → 실시간 화면 동기화 순으로 기능을 쌓아 올렸다. 이 과정에서 터치 인터랙션 구현 역시 터치 이벤트(Start/End/Move/Cancel) 확인 → 시작·끝점 좌표 추출 → 좌우 방향 판별 → 페이지 전환 → 이동 속도 계산 → 애니메이션 구현처럼 더 잘게 쪼갠 단계별 목표로 나누어, 기능 구현 단계에서는 완성도보다 속도를 우선하는 Lean 프로세스 원칙을 적용했다.

듀얼스크린 뷰어 이후에는 여러 대의 디바이스를 이어붙여 화면을 확장하는 **멀티 스크린 디바이스**로 실험을 확장했다. 디바이스를 맞대면 자력 센서로 서로의 위치·방향을 계산해 동기화하는 아이디어가 가장 이상적이었으나 기술적 한계로 구현하지 못했고, 대안으로 두 손가락으로 각 디바이스를 동시에 터치해 좌표를 맞추는 방식과, 두 화면에 걸쳐 선을 긋는 스와이프 제스처로 연결하는 방식을 구현했다. 스와이프 방식은 디바이스 간 Y좌표가 어긋나는 문제(포인트 간 기울기를 계산해 중간값으로 보정)와 iOS 알림센터·제어센터로 인해 상하 스와이프가 자유롭지 않은 문제(가로 스와이프만 허용)를 실무적으로 우회했다. 다중 디바이스 간 직접 통신 레퍼런스를 찾지 못해 결국 서버를 경유해 각 디바이스의 터치 이벤트와 위치·크기 정보를 교환하고 전체 해상도를 계산하는 구조를 택했다. 개발 도중 유사한 컨셉의 상용 서비스(Mosaic, Junkyard Jumbotron 등)가 이미 존재한다는 사실을 알게 됐지만, 완성까지는 마무리하기로 하고 프로젝트를 정리했다.

## 핵심 내용
- **LeanUXLab**의 멀티 스크린 디바이스 실험: 여러 디바이스를 네트워크로 연결해 하나의 콘텐츠를 공유하는 인터랙션 연구
- 출발점: 종이책처럼 두 페이지를 동시에 보는 전자책에 대한 랩 멤버의 요구, foldable 디바이스에 대한 전망
- 1단계 **듀얼스크린 PDF 뷰어**: PDF 렌더링 → 디바이스간 통신 → 실시간 동기화 순으로 기능을 쌓는 **MVP** 접근
- 터치 인터랙션도 이벤트 확인 → 좌표 추출 → 방향 판별 → 전환 → 속도 계산 → 애니메이션 순으로 세분화해 단계별 구현
- 완성도보다 속도를 우선하는 Lean 프로세스 원칙: "기능 구현을 목표로 할 때는 관대해져야 한다"
- 디바이스 동기화 방식: (실패) 자력 센서 기반 위치·방향 계산 → (채택) 2점 터치 좌표 매칭, 화면 간 스와이프 제스처
- 스와이프 방식의 실무적 보정: Y좌표 오차는 기울기 계산으로 중간값 보정, iOS 상하 스와이프 제약으로 가로 스와이프만 허용
- 디바이스간 직접 통신 레퍼런스 부재로 서버 경유 방식(터치 이벤트·위치·크기 정보 교환 후 전체 해상도 계산) 채택
- 개발 중 Mosaic, Junkyard Jumbotron 등 유사 상용 서비스의 존재를 뒤늦게 발견 — 리서치의 중요성을 되짚는 계기
